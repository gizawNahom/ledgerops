## An overdraft, and a check on the books

The first panel above is a refused overdraft. Move more than an account holds
and the request is refused, and the response says which account, what it has,
and what you asked for. After `make demo-01`, `alice-01` holds 50.00. The
panels leave out headers; real calls send an `Authorization` header and an
`Idempotency-Key`.

The second panel asks whether the books balance. One request checks every entry
in the ledger.

The service runs this check on itself. An independent verifier is on the
roadmap.

If an account's stored balance doesn't match its entries, the check says so
and names the account. The operator console shows it:

## A balance column works until it doesn't

Most teams that need balances start with a `balance` column and two `UPDATE`
statements. It holds up until a request times out and is retried, two requests
spend the same money, or a write fails halfway. Then value is created or
destroyed, and nobody can reconstruct what happened.

Three things that go wrong:

- **A double charge** after a timeout and a retry.
- **A negative balance** shipped under load.
- **A retrofit.** Putting a real ledger under production data that is already
  wrong is much harder than starting with one.

ledgerops does the bookkeeping part from day one, for wallets, credits and
loyalty points. It cares only that units are conserved, not what a unit means.

## What it guarantees

<div class="guarantees">

- **Conservation.** Every transaction's legs sum to zero, in integer minor
  units.
- **No overdrafts on wallet accounts, even under concurrency.** Funds are
  checked under row locks taken in a fixed order.
- **Append-only entries.** `UPDATE` and `DELETE` on entries are revoked from
  the service's database role, and a trigger refuses them too. Someone who
  holds the migration role or database admin access isn't covered by this.
  Hash-chained tamper evidence is on the roadmap.
- **Safe retries.** The same `Idempotency-Key` returns the original
  transaction instead of posting twice.
- **Tenant isolation.** A tenant is a separate set of accounts with its own
  API key. Each tenant's key sees only its own accounts and entries.
- **Cross-tenant transfers need both tenants to agree.** An operator-authorized
  link between the two tenants, plus a registered counterparty.

</div>

## What isn't there yet

ledgerops is pre-1.0. The core is complete and covered by property-based,
race and crash tests, but it isn't ready for production yet.

- One currency (USD).
- Two-leg transfers only. No holds, no webhooks, no metadata on transfers.
- No TLS in the service itself (run it behind a proxy), no OpenAPI spec, no
  tenant key rotation.
- The books check is run by the service itself. An independent verifier is on
  the roadmap.
- One very busy account is the first limit you'll hit. In the last load test,
  p95 latency was 923 ms against a 500 ms target, because concurrent transfers
  on the same account queue behind each other.
- Not yet run in production.

## Run it

```bash
make up
make demo-01
```

Docker, `make` and curl. The target is under five minutes from a clean
checkout. CI times the demo run and reports it; it doesn't fail the build if it
runs over.
